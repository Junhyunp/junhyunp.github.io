### 1. 하드웨어 격리 VM으로 에이전트 코드 샌드박싱 — smolvm

**무엇**
`smol-machines/smolvm` 은 libkrun 기반 하드웨어 가상화로 서브초 콜드스타트를 내는 경량 VM 툴이다(Hypervisor.framework/KVM/WHP, OCI 이미지 호환, Smolfile 로 설정). "격리가 기본값"을 내세우며 신뢰 못 할 코드 실행에 쓰인다. Simon Willison 이 2026-08-19 자 리서치 글에서 이걸 AI 에이전트가 생성한 Python/JS 를 격리 실행하는 샌드박스로 테스트했다는 것이 이번에 포착된 계기다.

**출처**
- [Research: smolmachines / smolvm as a sandbox for untrusted Python & JavaScript](https://simonwillison.net/2026/Aug/19/smolmachines-untrusted-sandbox/) — Simon Willison, 2026-08-19 (WebSearch 스니펫으로만 확인, 원문은 egress 차단으로 못 열어봄)
- 1차 출처: [smol-machines/smolvm](https://github.com/smol-machines/smolvm) — GitHub 공식 레포, 직접 열어 확인. ★5.6k, Apache-2.0.

**왜 쓸 만한가**
이 블로그의 Tech 축에 붙는 레포·도구 리뷰 소재다. Tech 카테고리가 상대적으로 얇아(#33 OpenClaw, #34 Prime Agent 정도) 균형상 값어치가 있고, "에이전트가 만든 코드를 어떻게 안전하게 실행할까"는 #19(사내 데이터 반입 전 체크리스트), 하네스 시리즈(#34~36)와도 맞물린다.

**검증** — 미확인
공식 레포를 직접 열어 smolvm 자체(무엇인지, 기술 구조, 스타 수, 라이선스)는 확인했다. 하지만 이번 소재의 실제 뉴스 포인트인 **Willison 의 실험 자체**(구체적으로 무엇을 테스트했는지, 콜드스타트 0.6~1.5초·웜 실행 50ms 라는 수치, "Claude Fable 5 가 /dev/kvm 이 없는 걸 알아채고 대신 GitHub Actions 워크플로우를 작성해 푸시했다"는 일화)는 `simonwillison.net` 이 12일째 egress 차단이라 WebSearch 스니펫으로만 봤다. 이 수치·일화는 글을 쓰기 전 원문에서 반드시 다시 확인해야 한다.

### 2. 에이전트 스킬은 왜 통하다 안 통하는가

**무엇**
"Demystifying Agent Skills: Why They Work—Until They Don't" (arXiv 2608.14036, Zhiyuan Jiang 외 8명). 에이전트에게 과거 궤적을 절차화한 "스킬"을 주면 왜 도움이 되는지를 통제 실험으로 뜯어봤다. 핵심 발견: 스킬이 도움이 되는 사례의 65.7%는 "절차 고정"(무엇을 먼저 할지, 어떤 도구를 쓸지, 무엇을 확인할지) 때문이고, "몰랐던 지식을 알려줘서"는 4.5%뿐이었다. 반대로 에이전트가 스킬 지시를 무시하거나 잘못 적용하는 "invocation failure" 사례도 10% 존재했다.

**출처**
- [\[2608.14036\] Demystifying Agent Skills: Why They Work-Until They Don't](https://arxiv.org/abs/2608.14036) — arXiv, 2026-08 (원문은 egress 차단으로 못 열어봄. WebSearch 스니펫 다수 및 X/HyperAI 미러가 같은 수치를 인용)
- 1차 출처: [zhiyuanjiang04/demystify-agent-skills](https://github.com/zhiyuanjiang04/demystify-agent-skills) — 논문 공식 코드 레포. 직접 열어 제목·저자·핵심 수치(65.7%/4.5%/10%)를 확인했다.

### 3. StateM — 하네스 스케일링만으로 터미널 벤치마크 95.3%

**무엇**
"StateM: Reaching 95.3% Raw Accuracy, or a $15 Frontier Run, on Terminal-Bench 2.1 via Harness Scaling" (arXiv 2608.15089, Ziheng Qin 외). 모델 가중치를 전혀 안 바꾸고 에이전트 실행을 "상태·전이·검증 체크포인트"로 명시적으로 쪼개는 CLI 하네스만 얹었더니, GPT-5.6 Sol xhigh 기준 Terminal-Bench 2.1 에서 95.28%(424/445) 를 냈고 비용은 기준선 $574.68 대비 약 $15 로 줄었다는 주장.

**출처**
- [\[2608.15089\] StateM: ...](https://arxiv.org/abs/2608.15089) — arXiv, 2026-08 (원문은 egress 차단. Hugging Face Papers/X 스니펫으로 포착)
- 1차 출처: [henryqin1997/statem](https://github.com/henryqin1997/statem) — 공식 코드 레포. 직접 열어 저자·수치(92.1% / 95.28% / 88.76%, 비용 $15 vs $574.68)를 확인했다.

**왜 쓸 만한가**
harness-engineering → Continual Harness(#35) → AutoDesign/DarwinX(#36) 로 이어진 "하네스 3부작"의 자연스러운 4번째 편이다. 특히 "모델을 안 바꾸고 하네스만 스케일링해도 이만큼 오른다"는 주장은 지금까지 다룬 자기개선/탐색형 접근과 각도가 다르다(구조화된 상태 머신 vs 탐색·co-learning).

**검증** — 확인됨
공식 GitHub 레포를 직접 열어 저자명·핵심 벤치마크 수치를 확인했다. arXiv 원문 자체는 egress 차단으로 못 열었으므로, 실제로 쓸 때는 비교 기준선(GPT 레퍼런스가 무엇인지)과 "$574.68" 산정 방식을 원문에서 한 번 더 확인해야 한다.
